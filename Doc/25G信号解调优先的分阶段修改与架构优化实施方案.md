# 25G 备赛导向的结构整理与信号解调扩展方案

> 日期：2026-07-25  
> 适用工程：`25G_PL`、`25G_PS`，Zynq-7020  
> 目标：透明、好懂、好调用、易修改、易定位问题，并尽量覆盖不同信号类赛题  
> 基线：当前文档所述功能均已完成上板实测，本文不再把已有功能当作待验证风险

## 一、先明确本次改造的性质

这不是一次面向产品上线的架构升级，也不是为了追求“完整软件工程”而重建系统。

本次改造的本质是：

> 把目前已经能工作的 PL、DMA、FFT、IQ 和 DDS 功能整理成一套比赛现场容易理解、容易组合、容易替换参数、出了问题能快速定位的工具箱。

因此，判断一项改动是否值得做，只看五件事：

1. 能否减少比赛时需要同时理解的文件数量；
2. 能否让一个功能通过少量 API 调用完成；
3. 能否通过修改配置而不是修改底层代码适配新题；
4. 能否在串口日志中迅速判断问题位于 ADC、DMA、算法、IQ 还是 DDS；
5. 是否保留当前已经上板验证成功的能力。

不以以下事项作为当前目标：

- 不追求产品级多层服务架构；
- 不为了形式完整引入复杂事件总线、插件系统或动态注册；
- 不默认改成 SG/cyclic DMA；
- 不默认重写 PL 数据通路；
- 不把每个算法都硬件化；
- 不一次性完成所有调制方式；
- 不在重构期间顺手改动已经工作的底层接口和参数。

## 二、对当前工程的判断

当前工程已经具有足够好的备赛基础：

```text
AD9226 → FIFO → AXIS → DMA → PS 原始采样
                         └→ FFT 与双分量识别

ADC 样本 → PL IQ 积分 → AXI-Lite → PS 幅相计算

PS → BRAM 原子提交 → 双 DDS → AD9767
```

这些功能均以当前上板实测结果为准，后续结构调整只做行为保持，不重新讨论它们“是否能工作”。

当前真正影响备赛效率的不是底层功能不足，而是：

1. 硬件调用、业务状态机、诊断打印和算法调用混在同一个流程中；
2. PS 端功能虽然已经拆成多个 `.c/.h`，但缺少一个统一、明显的调用入口；
3. 与旧题有关的超时、波形类型和 DDS 默认设置仍未全部迁入题目 profile；
4. 新题到来时，容易复制一套主流程再改，最终产生多个相似但不一致的版本；
5. 当前文档偏重说明已有功能，尚未给出“比赛时如何快速组合”的软件结构。

所以近期应优先整理 PS 端，而不是先增加新的 PL IP。

## 三、总体方案：一个入口、三层结构、多个模式

## 3.1 一个入口

应用层只包含一个公共头文件：

```c
#include "signal_api.h"
```

比赛主流程通过 `signal_api.h` 完成：

- 系统初始化；
- ADC 帧采集；
- 基础参数测量；
- 现有双分量识别；
- PL IQ 测量；
- AM/ASK/FSK/FM 解调；
- DDS 输出；
- 状态查询和错误恢复。

这里的“大 API 调用库”指的是一个统一的功能库和公共入口，不建议把全部实现塞进一个几千行的 `signal_api.c`。外部看起来是一个库，内部仍按功能分文件，出了问题可以直接进入对应模块。

## 3.2 三层结构

只保留三层，避免层次过多：

```text
比赛模式层 Modes
    ↓ 只调用 signal_api.h
统一 API 层 Signal API
    ↓ 直接组合现有驱动和算法
底层功能层 Drivers + Algorithms
```

### 比赛模式层

描述“这道题要做什么”，不直接操作寄存器和 DMA。

例如：

- 原有双分量信号分离模式；
- 通用参数测量模式；
- 微弱信号/IQ 模式；
- AM/ASK 解调模式；
- FSK 解调模式；
- FM 解调模式；
- DDS 回环自测模式。

### 统一 API 层

描述“系统能提供什么能力”，负责按正确顺序组合底层模块。

例如一次 `signal_capture()` 内部完成：

```text
必要的帧对齐 → Cache 处理 → DMA 接收 → monitor 快照 → 返回帧和状态
```

模式层不再自己拼接这些步骤。

### 底层功能层

保留当前已经工作的模块，例如：

- `dma_utils`；
- `iq_demodulator`；
- `dds_control`；
- `fifo_monitor`；
- `button_input`；
- `signal_analysis`；
- 后续增加的通用 DSP 小模块。

底层模块之间尽量互不调用，统一由 API 层组合。这样调用方向始终从上到下，定位问题时不会来回跳转。

## 3.3 多个模式，而不是多个工程

不同赛题尽量共用一个工程，通过模式和配置切换：

```c
typedef enum {
    SIGNAL_MODE_SEPARATOR,
    SIGNAL_MODE_MEASURE,
    SIGNAL_MODE_LOCKIN,
    SIGNAL_MODE_AM,
    SIGNAL_MODE_ASK,
    SIGNAL_MODE_FSK,
    SIGNAL_MODE_FM,
    SIGNAL_MODE_SELF_TEST
} signal_mode_t;
```

每个模式只实现一个清楚的入口：

```c
int mode_separator_run(signal_api_t *api);
int mode_measure_run(signal_api_t *api);
int mode_lockin_run(signal_api_t *api);
int mode_am_run(signal_api_t *api);
int mode_fsk_run(signal_api_t *api);
```

正式比赛时，可以删除不需要的模式，也可以只在 `app_config.c` 中选择默认模式，不需要复制整个工程。

这样每一步都小，出了问题容易回退。

## 五、统一 API 应该长什么样

## 5.1 API 对象

使用一个系统对象集中保存运行状态，逐步替代散落的全局变量：

```c
typedef struct {
    XAxiDma dma;
    arm_rfft_fast_instance_f32 fft;
    iq_demodulator_t iq;
    dds_control_t dds;
    button_input_t buttons;

    signal_mode_t mode;
    signal_error_t last_error;
    u32 capture_count;
    u32 dma_error_count;
    u32 bad_frame_count;
} signal_api_t;
```

为了透明，第一阶段不做完全不透明的 handle，也不做动态内存。结构体字段可以直接调试观察，所有缓冲区继续静态分配。

## 5.2 第一版公共函数

第一版只需要以下接口：

```c
int signal_api_init(signal_api_t *api);
int signal_api_set_mode(signal_api_t *api, signal_mode_t mode);

int signal_capture(signal_api_t *api, signal_frame_t *frame);
int signal_measure_basic(const signal_frame_t *frame,
                         signal_basic_result_t *result);
int signal_identify_components(signal_api_t *api,
                               const signal_frame_t *frame,
                               signal_analysis_result_t *result);

int signal_iq_measure(signal_api_t *api,
                      const signal_iq_config_t *config,
                      signal_iq_result_t *result);

int signal_demodulate(const signal_frame_t *frame,
                      const signal_demod_config_t *config,
                      signal_demod_result_t *result);

int signal_dds_apply(signal_api_t *api,
                     const signal_dds_pair_t *config);
int signal_dds_stop(signal_api_t *api);

int signal_get_status(signal_api_t *api,
                      signal_status_t *status);
int signal_recover(signal_api_t *api);
const char *signal_error_string(signal_error_t error);
```

函数数量不宜继续快速增长。只有至少两个模式都会使用的能力，才提升到公共 API；单个模式的辅助函数留在模式或算法文件内。

## 5.3 数据结构比函数数量更重要

所有结果都使用明确结构体，不用大量输出指针：

```c
typedef struct {
    const u16 *samples;
    u32 sample_count;
    float32_t sample_rate_hz;
    u32 frame_sequence;
    int frame_valid;
} signal_frame_t;

typedef struct {
    float32_t dc_code;
    float32_t rms_code;
    float32_t ac_rms_code;
    u16 minimum;
    u16 maximum;
    u16 peak_to_peak;
    u32 saturated_count;
} signal_basic_result_t;

typedef struct {
    float32_t carrier_hz;
    float32_t symbol_rate;
    float32_t modulation_index;
    float32_t confidence;
    u32 output_count;
    signal_error_t status;
} signal_demod_result_t;
```

当题目改变时，优先增加或调整配置和结果结构，不直接修改多个底层函数参数。

## 六、配置整理：通用性主要来自配置，而不是复杂抽象

## 6.1 消除剩余旧题硬编码的顺序

不需要一次性删除所有宏，按以下顺序迁移：

1. 双分量数量；
2. 正弦/三角波类型；
3. 18 秒超时；
4. DDS 固定幅度和相位设置；
5. 为通用测量、弱信号、AM、ASK、2FSK、FM 的零值占位 profile 填入题目参数。

原有专用模式继续使用原参数，新模式使用新的 profile。这样不会为了通用化破坏已经验证的旧题功能。

## 七、信号解调方向的简化路线

解调能力优先在 PS 上形成通用算法积木。只有实测 CPU 速度不够，或题目明确要求连续高速数据时，才把确定的瓶颈下沉到 PL。

## 7.1 先建立四个公共算法积木

### 载波检测

复用现有 FFT，在给定频带内寻找载波或两个 FSK 频点。去掉旧模式的强制 5 kHz 吸附后，可作为通用载波估计。

统一接口：

```c
int carrier_detect(const signal_frame_t *frame,
                   const carrier_config_t *config,
                   carrier_result_t *result);
```

### 数字混频

在 PS 中提供简单 NCO，将指定载波搬移到零频：

```text
x[n] × cos(ωn) → I
x[n] × sin(ωn) → Q
```

第一版使用递推振荡器或查表，不必追求复杂 DDS 框架。

### 简单低通和抽取

准备一组容易理解的 FIR 或一阶/二阶 IIR：

- 调试时可以关闭；
- 系数和截止频率集中定义；
- 每个滤波器有独立测试向量；
- 不在多个解调器中各复制一份。

### 结果置信度

所有解调器统一给出：

- 是否有有效载波；
- 输入是否饱和；
- 结果幅度；
- 置信度；
- 失败原因。

比赛现场比“永远返回一个数”更容易定位问题。

## 7.2 调制方式实现顺序

### 第一优先：AM 与 ASK/OOK

原因：结构简单、复用率高、容易用示波器和串口同时判断。

```text
原始帧 → 载波估计/已知载波 → I/Q 混频 → 低通
       → sqrt(I²+Q²) → 去直流 → AM 包络
       → 自适应阈值          → ASK/OOK 判决
```

若调制很慢，也可以直接使用当前 PL IQ 的连续窗口结果观察包络变化；若调制带宽较高，则使用原始 DMA 帧在 PS 做混频。

### 第二优先：2FSK

准备两种简单方法，根据题目选择：

1. 两个 Goertzel/相关器比较能量；
2. 复基带相位差分估计瞬时频率。

第一种更直观、容易调试，优先作为比赛模板。只有频偏范围较大或连续性要求高时再使用第二种。

### 第三优先：FM

先在保存的原始帧和连续多帧上实现：

$$
\Delta\phi[n]=\arg\left(z[n]z^*[n-1]\right)
$$

FM 对帧间连续性要求高，因此先评估当前 Simple DMA 轮询是否满足题目刷新率。若不满足，再做最小的 DMA 中断双缓冲，不直接跳到 SG DMA。

### 按题目再做：DSB-SC/BPSK

这类题需要处理载波相位和可能的 180°模糊。建议保留接口位置，但不在当前阶段提前实现 Costas、Gardner、QPSK 等完整通信链路。

## 7.3 现有 PL IQ 的定位

当前 PL IQ 已完成上板验证，应把它作为稳定公共能力保留：

- 已知频率的幅相测量；
- 微弱信号积分；
- 少量频点扫描；
- FFT 找到频率后的精确测量；
- AM 慢包络或慢变化参数观察；
- DDS 回环幅相测试。

PS 侧需要补齐的是调用形式，而不是立即重写 IP：

```c
int signal_iq_measure(...);
int signal_iq_scan(...);
int signal_iq_measure_average(...);
```

其中 `measure_average` 在 PS 读取多次结果，返回均值、方差和有效次数，便于微弱信号题直接使用。

## 八、PL 端的处理原则

## 8.1 近期不改主数据通路

在 PS 结构整理和解调原型完成前，保留：

- 当前 AD9226 采集；
- 当前 FIFO；
- 当前 AXIS 帧；
- 当前 DMA；
- 当前 IQ；
- 当前 DDS BRAM 原子提交。

PL 端近期只允许两类改动：

1. 增加必要的状态计数或版本号；
2. 当 PS 实测已经证明某个算法确实成为瓶颈时，下沉一个明确、独立的小模块。

## 8.2 何时才增加流式 DDC

同时满足以下条件时才增加：

1. 题目确实需要连续 AM/FM/PSK 基带，而不是间歇参数测量；
2. PS 原始帧实现已经正确；
3. CPU 耗时或 DMA 空洞已有实测数据；
4. 已确定载波范围、基带带宽和抽取率；
5. 能明确说明新增模块的输入、输出和调试信号。

若需要，第一版 DDC 只做：

```text
NCO → I/Q 乘法 → 简单低通/抽取 → 16 位 I/Q 输出
```

不同时加入 AGC、Costas、符号同步、协议解析和复杂 AXIS 路由。

## 8.3 PL 模块透明性要求

新增模块必须满足：

- 一个模块只承担一个主要功能；
- 参数写在模块头部并给出单位；
- 输入输出命名直接表达含义；
- 有 `valid/ready` 或清楚的采样使能；
- 饱和和丢样有计数；
- testbench 能单独运行；
- 不把关键状态藏在生成 IP 内部而无外部观察点。

## 九、问题定位体系

不建立复杂日志框架，只统一日志格式和错误码。

## 9.1 统一错误码

```c
typedef enum {
    SIGNAL_OK = 0,
    SIGNAL_ERR_ARGUMENT,
    SIGNAL_ERR_ADC_INVALID,
    SIGNAL_ERR_FRAME_INVALID,
    SIGNAL_ERR_DMA_START,
    SIGNAL_ERR_DMA_TIMEOUT,
    SIGNAL_ERR_FIFO_BLOCKED,
    SIGNAL_ERR_FFT,
    SIGNAL_ERR_CARRIER_NOT_FOUND,
    SIGNAL_ERR_IQ_TIMEOUT,
    SIGNAL_ERR_DEMOD_NO_SIGNAL,
    SIGNAL_ERR_DEMOD_LOW_CONFIDENCE,
    SIGNAL_ERR_DDS_COMMIT
} signal_error_t;
```

错误码只描述第一失败点，不在多个层次重复打印同一个错误。

## 9.2 快速定位表

| 现象 | 第一检查点 | 第二检查点 |
| --- | --- | --- |
| ADC 数值不变 | `[ADC]` min/max/change | AD9226 时钟和 valid |
| DMA 超时 | `[DMA]` 状态 | `[FIFO]` AXIS valid/frame |
| 首帧异常 | 帧长度和对齐状态 | FIFO/AXIS frame 增量 |
| FFT 找不到载波 | ADC 范围和饱和 | 搜索 profile 与频带 |
| IQ 幅相异常 | `RESULT_PINC`、样本数 | 输入频率与校准 |
| AM 包络不对 | 载波估计 | 低通截止频率 |
| FSK 误判 | 两频点能量 | 符号长度和阈值 |
| FM 噪声很大 | 基带幅度 | 频偏范围和帧连续性 |
| DDS 无输出 | commit 序号 | BRAM 快照与 RUN |

## 十、具体修改顺序

## P0：先把现有工程整理清楚

### P0-1：建立统一 API

操作：

1. 新增 `signal_api.h/.c`；
2. 先包装现有 DMA、IQ、DDS、monitor；
3. 原有分离模式改为只调用公共 API；
4. 保证串口行为和上板结果不变。

完成标志：阅读一个模式文件即可看懂完整业务流程，不需要同时打开底层寄存器驱动。

### P0-2：集中类型和错误

操作：

1. 新增 `signal_types.h`；
2. 新增 `signal_errors.h`；
3. 让统一 API 返回第一失败点，不再只返回笼统的 `XST_FAILURE`。

完成标志：任一 API 失败都能通过一个错误码和一个模块前缀定位。

### P0-3：补齐题目 profile

操作：

1. 为现有通用测量、弱信号、AM、ASK、2FSK、FM 占位项填入实际参数；
2. 将剩余题目相关超时、波形类型和 DDS 默认设置移入 profile；
3. 模式只读取 profile，不自行定义魔法数字。

完成标志：修改载波范围和判决参数不需要编辑底层驱动或算法源文件。

## P1：增加通用测量和解调积木

### P1-1：基础测量

增加：DC、RMS、AC RMS、Vpp、饱和点数。它们既能直接应对参数测量题，也能作为所有解调模式的输入健康检查。

### P1-2：通用载波检测

复用现有 FFT，允许 profile 控制频带、峰数量、是否栅格吸附。不改原专用算法，另加轻量通用入口。

### P1-3：数字混频和简单滤波

实现可单独测试的小函数，为 AM、FSK 和 FM 共用。优先清楚正确，不先追求极限优化。

### P1-4：AM/ASK 和 2FSK 模板

先完成这两类，提供合成数据自测和板上信号源测试入口。每种解调只放题目相关判决，公共处理全部复用前述积木。

## P2：提高现场可修改性

### P2-1：最小串口命令

```text
status
profile list|select
capture
measure
iq <freq> <window>
demod am|ask|fsk|fm
dds ...
counters
recover
selftest
```

第一版使用简单字符串匹配即可，不做复杂命令框架。

### P2-2：结果统一输出

所有模式统一输出：

```text
模式、profile、载波、幅度、置信度、错误码、处理耗时
```

这样更换算法后仍可用同一种方式对比。

### P2-3：准备常用测试数据

为 AM、ASK、FSK、FM 各保留少量代表性数据：

- 理想输入；
- 有 DC；
- 有噪声；
- 低幅度；
- 轻微频偏。

目的不是建立庞大测试体系，而是保证比赛现场修改参数后能快速判断有没有把基本功能改坏。

## P3：只有遇到明确瓶颈时再做

- DMA 中断双缓冲；
- PL 流式 DDC；
- 更长的连续环形缓冲；
- Costas 环；
- 符号同步；
- 自动量程硬件；
- 双 ADC 网络分析；
- 更复杂的 UI。

这些不是禁止项，但不能挤占当前结构整理、API 和通用算法模板的时间。

## 十一、建议的近期执行安排

| 顺序 | 内容 | 预计净开发量 | 结果 |
| ---: | --- | ---: | --- |
| 1 | 建立 `signal_api`，包装采集/IQ/DDS/状态 | 2～3 天 | 一个头文件调用系统 |
| 2 | 统一类型和错误码 | 1～2 天 | 问题容易定位 |
| 3 | 补齐占位 profile 并迁移剩余题目参数 | 1～2 天 | 参数容易替换 |
| 4 | 增加基础测量和通用载波入口 | 2～3 天 | 通用测量底座 |
| 5 | 数字混频、低通、AM/ASK | 3～5 天 | 第一套解调模板 |
| 6 | 2FSK 模板 | 2～4 天 | 第二套解调模板 |
| 7 | 最小 CLI | 2～3 天 | 现场无需频繁重编译 |
| 8 | 根据实测决定 FM、DMA 双缓冲或 PL DDC | 待定 | 不提前增加复杂度 |

每完成一项，只做与改动范围相称的回归：

1. 能编译；
2. 原有上板流程仍正常；
3. 新 API 返回值和日志正确；
4. 对应模式的少量代表性数据通过。

不要求每一步都重新做长时间验收或完整系统测试。

## 十二、实施时必须遵守的简化规则

1. 一个模式文件只描述一种业务流程；
2. 一个算法文件只解决一个明确数学问题；
3. 模式层禁止直接访问寄存器；
4. 底层驱动禁止知道 AM、FSK 等题目概念；
5. 公共 API 不暴露不必要的 Xilinx 驱动细节；
6. 所有可变题目参数进入 profile；
7. 已经上板工作的接口和默认参数在单独任务中才允许修改；
8. 重构和新增算法分开提交、分开测试；
9. 没有两个调用者的功能，不提前抽象成公共框架；
10. 能用一个清楚函数解决的问题，不增加回调、注册表或动态对象。

## 十三、最终目标形态

整理完成后，一个新的比赛模式应能写成：

```c
int mode_am_run(signal_api_t *api)
{
    signal_frame_t frame;
    signal_demod_config_t config;
    signal_demod_result_t result;

    signal_profile_get_am(&config);

    if (signal_capture(api, &frame) != SIGNAL_OK)
        return signal_api_last_error(api);

    if (signal_demodulate(&frame, &config, &result) != SIGNAL_OK)
        return result.status;

    signal_print_demod_result(&result);
    return SIGNAL_OK;
}
```

阅读这个文件就能知道 AM 模式做了什么；需要看采集问题时进入 `dma_utils`，需要看载波问题时进入 `carrier_detect`，需要看包络问题时进入 `am_ask_demod`，调用链清楚且没有重复代码。

最终希望形成的不是一套复杂平台，而是：

> 一套保留现有可靠 PL/PS 能力、通过单一 API 调用、通过 profile 快速改题、通过模块化日志快速定位问题的信号处理备赛工具箱。

近期最重要的三件事依次是：

1. 建立统一 `signal_api` 和清楚的模式文件；
2. 补齐统一类型、错误码和题目 profile；
3. 用通用载波检测、数字混频、简单滤波组成 AM/ASK 与 2FSK 模板。

完成这三项以后，再根据实际题目和实测性能决定是否增加连续 DMA、流式 DDC 或更复杂的同步算法。这更符合备赛的轻重缓急，也更能保证系统始终透明、好懂、好改。
